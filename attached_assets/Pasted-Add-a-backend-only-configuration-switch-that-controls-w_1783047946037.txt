Add a backend-only configuration switch that controls whether authentication is required for using the app. This configuration must not exist in the UI and must only be handled on the backend. The app currently allows usage without authentication; this switch must allow toggling between “authentication required” and “authentication not required”.
When authentication is required, all entry points from the homepage into the app must be blocked unless the user is authenticated via the existing Eitaa login system. If the user is not logged in, any button that leads into app usage must not proceed and must instead show a popup requiring login. This popup must include a “Login with Eitaa” button that uses the same existing login mechanism already present on the homepage. The login system must not be modified, tested, or mocked, as it only works in the deployed messenger mini-app environment via its SDK and is not accessible in Replit.
When authentication is not required, the app must behave normally without login enforcement.
Remove the Library tool completely from the application, including UI, backend references, and any asset or feature logic connected to it.
Replace the single Upload Image button on the homepage with three aligned buttons. On the left, a small square button containing a settings icon. In the middle, a rectangular button with the same height as the left button labeled “Select Image”, replacing the previous upload functionality. On the right, another small square button containing a “?” icon used for the guide/help system. These three buttons must be visually aligned and treated as a single grouped control.
After an image is selected using the “Select Image” button, the app must NOT immediately enter the editor. Instead, show a centered choice UI with two stacked rectangular buttons. The top button is “Edit Image” which continues the normal editor flow. The bottom button is “Use Saved Styles” which is only an entry point and will be implemented further later.
Fix Studio Mode layout behavior in the image editor. When switching to Studio Mode, the sidebar expands due to additional controls and text, which causes the undo/redo controls to overflow or move out of the visible screen. The layout must be adjusted so that all controls, including undo and redo, remain visible within the viewport in both Normal Mode and Studio Mode. Studio Mode must not break sidebar responsiveness or cause overflow of any controls.
Fix zoom behavior in the image editor. Zooming must allow smooth zoom-in and zoom-out behavior without restricting unzoom to a fixed percentage threshold. Users must always be able to return to their previous or original zoom level after zooming in. Zoom-out must not be clamped in a way that prevents restoring prior zoom state.
Add a Saved Styles system to the image editor. A Saved Style is a reusable preset that stores a snapshot of up to 10 editor objects and their order. Only tools from the following set are allowed in Saved Styles: crop, resize, flip, rotate, text, paint, filters, logo, watermark, picture-in-picture, add frame, and layers. Image adjustments such as brightness and contrast are part of Settings and must not be included in Saved Styles.
Saved Styles must enforce a hard limit of 10 objects inside the editor. This limit must be enforced during editing, not during saving. If a user attempts to add an 11th object, the action must be blocked immediately and a warning must be shown. The system must not allow bypassing this limit.
Each object in Saved Styles must store its properties and position using percentage-based coordinates relative to the image dimensions. The order of objects must be preserved exactly and must define rendering/layer stacking order.
When creating a Saved Style, the existing editor must be reused. A separate or new UI for a Saved Style editor must NOT be created. Only reuse the current editor interface and exclude tools that are not allowed in Saved Styles. Minor UI adjustments are allowed only to support restrictions, but the overall editor must remain unchanged. The user must edit using an example image rather than a blank canvas to make placement intuitive. The final Saved Style must be saved as a serialized snapshot of editor state only.
When applying a Saved Style, all stored objects must be reinserted into the editor in the same order and positions, and the user must be able to continue editing or export using existing functionality.
Add a logo management system tied to the authenticated user. Each user can store a maximum of 5 logos. All logos must be stored in the database. If a logo exceeds 500kB, it must be automatically optimized/compressed until it is under 500kB while preserving acceptable visual quality.
Add a Settings system tied to the authenticated user identity. Settings must include only the following: editable username, dark/light theme toggle, Saved Styles management (view/remove/add within limit of 5), and logo management (view/remove/add within limit of 5). No additional settings are allowed.
Add a Guide system with two distinct sections. The Image Editor section must display all toolbar tools as horizontally scrollable square cards. Each card must visually represent the tool as shown in the UI, include the tool name, describe what it does, and explain when to use it. This section must directly map to all editor tools and act as a visual and functional reference.
The Saved Styles section must be step-based and must not use cards. It must explain why Saved Styles exist, how they work, how to create them, and how to apply them. It must include outcome-focused examples rather than only instructions. One example must demonstrate channel branding use cases where a logo and watermark (e.g. “@channelname” or “eitaa.com/channel”) are consistently applied across images. Another example must demonstrate alternative layouts where logo and watermark placement differ while still maintaining consistent branding behavior. The purpose is to show real-world output, not just explanation.
